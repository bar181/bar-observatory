Methodology & definitions (status vs coverage, the oracle)

Status is loss-detection: complete = no dead-letter loss recorded; partial = a loss or gap was measured; not_recorded = the channel produced no rows. Coverage is a separate axis: verified means an oracle measured completeness (hooks: bracketed + paired; transcripts: seq gapless + parents resolve + tool_use paired with tool_result; spans: closed + parents resolve); gap_detected names the shortfall; unverified means no oracle exists for that channel yet. A green status is never a coverage guarantee.

Where the numbers come from

Capture channels, explained

BAR Observatory can capture up to 6 independent channels. Each one is recorded (or not) independently — a channel with nothing in it doesn't mean the tool is broken, it means nothing was feeding it during this window. This flow shows all 6, real status, what each one is for, and the exact command to pull its evidence yourself.

Hooks — not recorded

Claude Code lifecycle events: SessionStart, PreToolUse, PostToolUse, Stop, SubagentStop.
Needs bar-hook wired into Claude Code's own hooks settings, running live during the session.
Verifybar query <db> --sql "SELECT COUNT(*) FROM hooks"

Events — not recorded

Structured log/metric events emitted by the runtime during a session.
Needs a live capture process running alongside the session; nothing ingests this from a saved transcript.
Verifybar query <db> --sql "SELECT COUNT(*) FROM events"

OTLP spans — not recorded

Distributed-trace spans (parent/child call structure, timing) via OpenTelemetry.
Needs bar-otlp's native gRPC receiver running and the session's tools configured to emit to it.
Verifybar query <db> --sql "SELECT COUNT(*) FROM spans"

Transcripts — partial · 9,132 rows

Every turn (user/assistant/tool_use/tool_result) from the 7 ingested .jsonl files — the source for nearly everything else in this report.
629 dangling parent(s) + 139 unpaired tool_use/tool_result — a real, measured structural gap in the raw JSONL, not an estimate.
Verifybar query <db> timeline --limit 0 or bar query <db> --sql "SELECT COUNT(*) FROM transcript_turns"

Requests — not recorded

Per-API-call detail: exact token counts, latency, model, from the wire — the authoritative source for cost.
Only bar-proxy, intercepting live Anthropic API traffic as it happens, can populate this. A saved transcript is not enough (see the token appendix below for why raw transcripts still carry some usage data anyway).
Verifybar query <db> --sql "SELECT COUNT(*) FROM requests"

Provider cost — not recorded

An authoritative per-token USD figure from the provider's billing API.
Subscription auth (ADR-024) exposes no such figure by design — BAR derives a labeled list-price estimate instead when token data exists; tokens + wall-clock stay the primary cost signal.
Verifybar query <db> --sql "SELECT COUNT(*) FROM requests"
Cost is computed from requests' token columns at render time, not stored in its own table — 0 rows here is why cost reads not_recorded.

Only transcripts was active this window — a retroactive bar ingest <db> <transcript.jsonl> pass over 7 saved sessions, not a live-wired capture. To light up the other 5 for a future session: wire bar-hook into Claude Code's hooks config and run bar-otlp / bar-proxy alongside it — see process/00-init.md and process/04-optional-modules.md in this repo.
