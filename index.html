BAR Observatory reads the record of a Claude Code session — every tool call, every task, every retry, every error that scrolled past — and prints it as a report you can actually check. What it is

Think of it as the black box on an aeroplane.

The flight recorder doesn't fly the plane and it doesn't second-guess the pilot. It writes down what happened, so that afterwards anyone can open it and find out.

An AI coding agent works the same way a very fast, very literal assistant does. You ask for something; it goes away and does hundreds of small things — opening files, running commands, handing work to helper agents, fixing its own mistakes — and then comes back with a summary of how it went.

That summary is written by the same agent that did the work. BAR Observatory reads the record of the work instead, and turns it into a plain report: what was attempted, what broke, what got done twice, and what it cost.

The short version: it's an itemised receipt for a session of AI work — and like a good receipt, it's the same every time you look at it, and it doesn't invent line items it doesn't have.

Problem 01

The summary isn't the evidence

The agent tells you what it intended. The session record holds what it actually did. Those are two different documents, and only one of them is checkable.

Problem 02

Failures scroll past

A command that timed out four hundred steps ago, inside a helper agent you never saw, is gone by the time it matters. It's still in the record — nobody reads the record.

Problem 03

There's nothing to hand anyone

No artefact to attach to a code review, show a client, give an auditor, or compare against last week's run. Just a terminal window you've since closed.

How it works

Four steps. Nothing leaves the machine.

You don't have to set anything up in advance. Claude Code already writes a transcript of every session to your own disk — BAR Observatory can read one you finished last month.

STEP 1

Point it at a session

Every Claude Code session leaves a transcript file on your computer. That file is the input.

STEP 2

Read and file it

bar ingest reads the transcript and files every event into a small local database — one file per run, portable and yours.

STEP 3

Print the report

bar report turns the database into a report. No AI is involved in this step, which is why the output never drifts.

STEP 4

Open it, or ask your agent

Read the HTML yourself, attach the Markdown to a review — or let your AI agent query the same database directly.

Why "deterministic" matters, without the jargon. Most tools that summarise AI work use AI to do the summarising, so the same session can produce a different write-up each time. BAR Observatory's report is calculated, not written. Run it again next year and you get identical output — which is what makes it usable as evidence rather than as an impression.

Advanced — the capture and render path

Transcript ingestion is the always-on path and requires no live capture. Hooks, the proxy, and the OTLP receiver are additional channels, opt-in by design. All channels converge on one SQLite store; the render path is a pure function of that store.

What you get

One database, three views, always in agreement.

  • report.html — the human view. Open this one first.
  • report.md — plain text, easy to diff or read over a terminal.
  • report.json — the machine version, structured and typed.

All three are rendered from the same database in the same pass, so they can't disagree with each other. Working samples ship in the repository under examples/ and are re-rendered from a real session every phase — they're never hand-written mock-ups. Full annotated walkthrough of every section, quoting the shipped example: wiki/human-html/report-guide.html.

Proof

Sixty failures, all of them still there months later.

Everything below came out of one genuine Claude Code session. Run the same commands against your own and you'll get your own numbers — that's the whole point.

"What silently failed?"

$ bar query <db> errors --limit 0
seq   excerpt

150   Bash rm -rf (guardrail refusal)
438   Agent type not found (sub-agent unavailable)
603   Exit code 143 (killed long-running command)
1490  2 matches, replace_all false (ambiguous edit)
1851  Read input not valid JSON (malformed tool call)

Guardrail refusals, a missing sub-agent, a killed command, ambiguous edits. Each with its exact position in the session and its original text. Nothing swallowed, nothing rounded away.

"What did it lean on, and is the recorder even working?"

$ bar query <db> tools
Bash 1,700+ · Edit 490+ · Read 410+ · …

$ bar report <session>.sqlite
wrote report.json report.html report.md

$ bar doctor <session>.sqlite
channels: transcript OK · tokens not_observed

Check the instrument before you trust the reading. bar doctor says plainly which channels had data and which were blind spots — rather than letting a gap look like a measurement.

An honest finding, published rather than buried. While writing this documentation we found that some tool results failed to reach the model's context yet were recorded correctly on the server side. BAR Observatory reads the session transcript — the server-side truth — so a delivery failure to the model doesn't appear in the report. It's disclosed here as a candidate for a future detector. A measurement instrument that hides its blind spots isn't one.

Reason 01

It works on the past

Every other approach needs you to have been recording at the time. This one reads the transcript already sitting on your disk.

Reason 02

It says when it doesn't know

An uncaptured channel prints as not_observed. Never a zero you might mistake for a measurement.

Reason 03

Your agent is a first-class reader

The same database is exposed to AI agents over MCP, so an agent can review its own last session without you copying anything.

Fit

Who this is for.

  • You run long or unattended AI coding sessions and want to know what happened in them.
  • You need evidence of AI work for a code review, a client, or an audit.
  • You're debugging multi-agent runs where failures hide inside helper agents.
  • You care that nothing leaves your machine.
  • You want your agent to learn from its own execution history, not its own summary of it.

And who it isn't.

  • You want a live dashboard while a run is still in progress.
  • You need fleet-scale aggregation across hundreds of runs and many machines.
  • You're evaluating prompt or model quality rather than what the agent did.
  • You're not using Claude Code.
Works with the network cable pulled out. Capture, storage, and reporting are all offline by construction — no server, no sync, no account. The one opt-in exception is bar interpret, clearly labelled and never required. Details for regulated and air-gapped environments: wiki/human-md/enterprise.md.

Get started

Your first report takes about a minute.

The easy way — inside Claude Code

The plugin wires everything up for you and adds five commands you can run without leaving your session.

/plugin marketplace add bar181/bar-observatory
/plugin install bar-observatory@bar-observatory
/bar-init

Then /bar-report whenever you want a report. /bar-doctor checks the recorder is working, /bar-query asks the database a direct question, and /bar-interpret produces the optional written summary.

The plugin needs the programs on your path:

cargo install bar-hook bar-mcp bar-observatory

The direct way — a terminal

No Rust yet? One line: curl https://sh.rustup.rs -sSf | sh

cargo install bar-observatory

# set up this project (safe to re-run)
bar init --dir .

# find a session you already ran
ls ~/.claude/projects/*/*.jsonl

# read it — no API key, no network
bar ingest .bar/ambient.sqlite <session>.jsonl

# print the report
bar report .bar/ambient.sqlite --out .

Open the .html file. That's your report. There's a one-script version too — see RUN.md in the repository.

Advanced — connect an agent over MCP

claude mcp add bar-observatory -- bar-mcp --db-root .bar

Twelve read-only tools over the per-run capture databases. Call get_hub first — it routes an agent to everything else in the record. Beyond one run: compare_conditions aggregates ledgers across every database under --db-root, and list_findings / recall_context read the reflection engine's stored recommendations and memory-graph recall — so a new session can start from what a previous one already learned, instead of re-discovering it. Full tool list and ground rules live in wiki/agent/AI-CONTEXT.md.

Advanced

Under the hood.

BAR Observatory is a thin bar CLI (crate bar-observatory) over a fifteen-crate bar-* engine. Crate source lives and publishes from a private working repository; the public repository is the front door, documentation, plugin, and contracts. Full write-up: wiki/human-md/architecture.md.

The determinism contract

  • No model in the render path. Report generation is a pure function of the capture database. Any interpreted output is a separate, optional command.
  • Byte-identical across formats. JSON, HTML, and Markdown render in one pass from one database, so they cannot disagree.
  • Typed contract. report.json is structured, typed output. A versioned JSON Schema for it ships in schemas/ but is currently out of sync with the live report shape — a known gap, disclosed rather than silently wrong.
  • Every claim resolves to a row. Facts carry identifiers back to the database that produced them.
  • Integrity artefacts. checksums/SHA256SUMS.txt and provenance/PROVENANCE.json ship with the repository.

Absence semantics

The schema carries an explicit absence state. A channel with no data renders as not_observed, never coerced to zero, empty, or unchanged. This is a design rule with teeth: a cost figure of $0.00 and a cost figure of not_observed mean entirely different things, and conflating them is how observability tools quietly lie. bar doctor exists to make the distinction visible before you read a report.

Capture channels

  • Transcript ingest — always on, zero network calls, works retroactively. The primary path.
  • Lifecycle hooks — 21 events, wired by the plugin. Unresolvable hook commands fail harmlessly and never block a session.
  • Proxy — opt-in ANTHROPIC_BASE_URL interception for request-level detail.
  • OTLP receiver — opt-in, native, for OpenTelemetry-emitting sources.

Known limits, on the record

  • Model-side delivery failures are invisible. Results that failed to reach the model's context but were recorded correctly server-side do not appear. Disclosed as a candidate detector.
  • Plugin binaries resolve via PATH. No release pipeline assembles per-platform binaries into the plugin zip yet.
  • Uncaptured channels stay uncaptured. Optional modules are off by default; the always-on path is transcript parsing only.

Questions

Frequently asked.

Does BAR Observatory send my code anywhere?

No. The main path reads a file that's already on your disk and makes zero network calls. There's no account, no API key, and no telemetry. Everything is a local SQLite file on your machine, and the source is MIT-licensed so you can check that claim rather than trust it.

Do I need an Anthropic API key?

No. Nothing in the capture, storage, or reporting path calls a model.

Can I get a report for a session I already ran?

Yes — and it's the quickest way to try it. Point it at any Claude Code transcript on your disk and you'll get a report straight away, even though nothing was recording at the time.

Where does Claude Code keep session transcripts?

In your ~/.claude/ folder, one .jsonl file per session, organised by project. ls ~/.claude/projects/*/*.jsonl will list them.

What does not_observed mean?

It means BAR Observatory had no data for that channel and is telling you so, rather than printing a zero you might mistake for a real measurement. Absence is reported as absence.

Is this a replacement for my existing monitoring?

No — it's a different job. Live dashboards and telemetry backends answer "what is happening across my systems right now." BAR Observatory answers "what happened in this one run, provably." Plenty of teams will want both.

What's the difference between the report and the interpretation?

bar report is the calculated layer: no AI, identical every time, safe to treat as evidence. bar interpret is an optional extra that writes a readable improvement summary in either an engineering or an executive framing. The evidence never depends on the interpretation.

Is BAR Observatory made by Anthropic?

No. It's an independent open-source project by Bradley Ross, built for Claude Code but not endorsed by or affiliated with Anthropic.

How do I get help?

Open an issue on the repository. Security reports have their own process in SECURITY.md, and contribution guidance is in CONTRIBUTING.md.
