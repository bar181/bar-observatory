A guide for junior developers

Your agent's excuses vs. the record.

Fifteen minutes, one real example, commands you can copy.

"Done! All tests pass, everything's working." You've seen that message. Sometimes it's true. Sometimes the agent tried something, it half-worked, it moved on, and the sentence is optimistic rather than accurate. The skill this page teaches isn't distrust — it's knowing where to look before you hit merge.

The core idea

A claim and a proof are not the same row.

BAR Observatory's task ledger records more than whether a task finished — it records how it knows. Every task carries a completion_evidence field, and it's usually one of these two:

self_reported

The agent said it finished. That's a real signal — but it's the same category of evidence as a teammate telling you "yeah, I tested it." Worth having. Not the same as proof.

measured

Pulled from something that independently happened — a real test-runner line, a command's actual exit code. This is the evidence that survives you asking "wait, how do we know?"

A real example, from the capture that ships with this project. 373 cargo test result lines were captured — 344 passed, 29 failed, and the run's last line was a pass. That "29 failed" is measured: it comes from the test runner's own output, not from the agent summarizing its own work. Three tests even flipped between pass and fail across the window — a real signal worth a second look, not necessarily a bug.

Try this before your next merge

Four commands, in the order you'd actually use them.

  1. Check the recorder is actually working. 
    bar doctor .bar/ambient.sqlite
    Before trusting a report, confirm there's a report to trust. This tells you honestly which channels captured data and which didn't — checking the instrument before reading it.
  2. See what actually happened, not what got summarized. 
    bar report .bar/ambient.sqlite --out .
    Open the .html file. The task ledger and rework-hotspots sections are the two worth reading first — they're where an optimistic summary and the actual record are most likely to disagree.
  3. Pull the errors directly. 
    $ bar query .bar/ambient.sqlite errors
seq   excerpt
----  -----------------------------------------------------------------
133   Permission to run `rm -rf …/target/debug` was denied by policy
453   String to replace not found. `README.md` was read 240 turns ago
690   Agent type 'requirements-validator' not found. Available: …
1035  File has not been read yet. Read `CHANGELOG.md` before editing it
1104  SyntaxError: Unexpected token '<' in JSON at position 0
…                                                     (60 row(s))
    Every failure the session hit, with its exact position, whether or not the agent chose to mention it in its own summary. Read them with a sceptical eye in both directions: the first row there is a guardrail doing its job, not a defect, and roughly a third of the sixty are like it.
  4. If something looks off, ask the raw database directly. 
    bar query .bar/ambient.sqlite --sql \
  "SELECT title, completion_evidence FROM tasks WHERE state='completed'"
    Read-only by construction — a write statement is refused by SQLite itself, so there's nothing to break by poking around.

The other thing worth checking

Where the agent circled back — and why that's not automatically bad.

A "rework hotspot" is a file the agent edited far more than the rest. In the capture that ships with this project, 77 of 482 repeat edits — more than the next four files combined — landed in a single file. That's not automatically a problem with the agent. It's frequently a sign that the task or the spec for that one file was underspecified, and the agent kept guessing until something stuck. It can just as easily be a file that was always going to need many passes. The report deliberately doesn't guess which — it shows you the concentration and lets you go and look.

Read it as

A question, not a verdict

"Why did this file take 77 edits?" is worth asking before you review the diff — it tells you where to look closest, not that the code is necessarily wrong.

What it's good for

Catching scope creep in your own asks

If every session on a particular file turns into a rework hotspot, the pattern is often about the instructions you're giving, not the agent's competence.

One honest caveat

This isn't a tool for catching your agent in a lie.

The record can be incomplete for reasons that have nothing to do with the agent's honesty. If a capture channel wasn't running, the report says not_recorded — not "nothing happened," just "nothing was captured." (There's a third word, not_observed, for a channel whose machinery exists but was never invoked here. Same lesson, one step further along.) Learn to read that distinction and you'll avoid the opposite mistake: treating an absence of evidence as evidence of a problem.

The rule that matters here: 0 failures means the evidence was checked and none were found. not_recorded means there wasn't enough evidence to check at all. Confusing the two in either direction — assuming the best or assuming the worst — is the mistake this tool exists to prevent.
