Wiki · report guide

What's actually in a report.

Every section below is annotated from the shipped example — session.report.json, which is literally what bar report wrote over the seven transcripts in examples/capture/. Not a mock-up written to look good: run the tool over the same capture and you get the same figures. Where a section is empty, that is shown too — an unbuilt feature reads not_observed, the same as an uncaptured channel, never silently omitted.

The project in the example, orbit, is a stand-in: the measurements are real, the repository is not.

The actual rendered report this page annotates. Open it yourself: session.report.html

Walkthrough

Each part, traceable to a row.

01

Stat bar

The header. Orientation before detail.

Six figures across the title plate — volume, outcome, cost in time — the numbers a reader needs before anything else. The real strip for this session:

7 sessions · 9,132 transcript turns · 3,171 tool calls
40 / 40 tasks completed · 60 error results · 322h 59m recorded window

Directly beneath it the report draws the composition of those 3,171 calls as a single banded strip — one band per tool, widest first — so the shape of the session is visible before a single table. Every band is also written out in prose and in the tool table further down, so the page still argues its case with scripting switched off.

02

Executive summary

One paragraph, assembled from fields — never composed by a model.

A single sentence stitched from real counters, not written prose:

Over 322h 59m, the session made 3,171 tool calls across 9,132
transcript turns, dispatched 40 sub-agent run(s), and captured
60 error result(s).

Compare this to bar interpret's output: that one is LLM-written prose, and is labeled as such wherever it appears. This one is template substitution over typed fields — swap the database, the sentence updates itself; nothing here was composed.

03

Key findings

What the detectors actually found, each with its own evidence line.

Four findings, each a plain claim with a supporting detail underneath it — not a single undifferentiated wall of text:

60 tool error(s) were captured — the failures are recorded, not swallowed.
  Worst: Bash ×45. One file absorbed the most churn: 77 edits.
  orbit/README.md — a refactor / test-coverage candidate. Validation was not fully green at capture end: 29 failing vs 344 passing.
  From real `test result:` lines (measured, not self-reported). 6 of 9 capture channels were not recorded this session.
  Uncaptured channels read "not recorded" — this is a transcript-only ingest.

Each of these traces to a section further down this page — the findings aren't a separate narrative, they're a summary of facts that are also shown in full.

04

Recommendations

Resolution-first, priority-tagged, grounded in the findings above.

Three recommendations, each tagged P1/P2/P3 by how directly it follows from captured evidence — not a generic best-practices list. The list is as long as the evidence supports and no longer; a session with nothing to flag gets a short one:

P1 Resolve the remaining failing tests before relying on the session's
  completion claims. P2 Review `orbit/README.md` (highest edit churn) for a refactor or missing
  test coverage. P3 Enable OTEL telemetry + hooks to capture tokens/cost, timeline,
  and coverage.
05

Task ledger

What was attempted, and how each item's state was determined.

40 tasks total this window — all 40 completed (100%, self-reported). Every row carries its own evidence type rather than a bare status:

state: completed
completion_evidence: self_reported
evidence_refs: [transcript:task-tool-calls]

self_reported is disclosed as exactly that — the task tool said "done," which is evidence of a claim, not independent proof of correctness. Compare that honestly against §08's validation evidence, which is measured from real test output instead.

06

Tool usage

Which tools, and how hard, ranked by real call counts.

Bash 1,706 · Edit 496 · Read 410 · TaskUpdate 209
TaskCreate 132 · Write 97 · Agent 40 · ToolSearch 19 · TaskOutput 16 · …

Seventeen distinct tools appear in the full record; this is the ranked head of that list, exactly as captured — nothing rounded, nothing merged, and the tail (down to Workflow ×1) is kept rather than collapsed into an "other" bucket.

07

Sub-agent dispatches

What got delegated, and to which agent type.

40 agent run(s) total, 8 distinct types
general-purpose ×17 · reviewer ×10 · docs-researcher ×5
requirements-validator ×3 · docs-curator ×2 · release-verifier ×1
skeptic-reviewer ×1 · unspecified ×1

A session that spawns helper agents can hide its real failure surface inside them — this section is why that no longer works. Every dispatch is counted by type, whether or not the parent session's own summary mentioned it.

08

Rework hotspots

Where effort concentrated — a signal about the work, not a score.

orbit/README.md — edited 77 times
orbit/index.html — edited 22 times
orbit/docs/guide/README.md — edited 16 times
orbit/docs/manifest.json — edited 16 times
…92 more files, 482 repeat edits in all

77 of that window's 482 repeat edits — more than the next four files combined — landed in one file. The report doesn't editorialize about why; it just makes the concentration impossible to miss, which is usually enough to prompt the right question.

09

Validation & flaky signals

Measured from real test output — not a self-reported "tests pass."

373 verdict line(s) (373 cargo) — 344 passed, 29 failed
last verdict: PASSED (measured, not self-reported)
unreadable_results: 0 flaky: 3 test(s) both passed AND failed this window
  round_trips_losslessly — 3 fails / 5 passes
  query_failures_are_disclosed_not_silent — 2 fails / 3 passes
  committed_hooks_match_generator — 1 fail / 2 passes

A test that flips between pass and fail across the same session is a real signal — could be a fix landing mid-session, could be a regression, could be flakiness. The report doesn't guess which; it surfaces the flip and lets a human or agent decide.

Two details in that block are there because of a real defect a user reported. The verdict count now names which runner matched — it used to describe every verdict as a cargo test result: line even on a pytest-only session. And unreadable_results counts tool outputs too large to be stored inline, which an earlier version could not read and silently left out of the total; verdicts are now extracted during ingest, while the full output is still in hand, so a failing run that produced a lot of output can no longer go missing. Where a store still predates that change, this section reports partial rather than a confident count.

The flaky list below it had the same problem in a nastier form. A test that flips inside a long run is exactly the flip worth knowing about, and it was exactly the one the old scan could not see — so the section answered "no flaky tests" with confidence. Per-test verdicts are now read at ingest too, and the section reports partial rather than "none" when it is working from a store it cannot fully read.

10

What's honestly not here yet

Unbuilt features disclosed as not_observed, not omitted.

not_observed
human_ai_recovery: "Not observed — human-vs-AI recovery
classification is not built yet." observations: "Not observed — micro-observation extraction and
silent-signal detection are not built yet; no findings are fabricated."

This is the clearest example on this page of the rule this whole project is built around: a capability that doesn't exist yet is stated as absent, in the same schema position a real finding would occupy — never a quietly empty section that looks like "nothing to report" when the honest answer is "not measured."

Capture & integrity

The two sections that let you trust the other ten.

11

Capture-channel honesty

Which channels actually had data.

transcripts: partial — 9,132 turns; 629 dangling parent(s), 136 unpaired tool_use/tool_result
hooks / events / spans / requests / file_history: not_recorded — no rows in this store
provider_cost_usd: not_recorded — no authoritative per-token USD available
plan_docs / raw_logs: not_observed — writer exists, nothing has invoked it here

One line in that block is about the recorder rather than the session: a tool output above the inline size cap has its body moved to a content-addressed file beside the database, and this row says how many. Only the body moves — every field that identifies the result stays, which is why an error in a huge output still counts as an error and still pairs with its call. That was not always true, and while it wasn't, the "unpaired" figure above was partly the recorder reporting damage it had done itself.

Nine channels, three states, and the difference between the last two is the whole point. Six read not_recorded because this was a transcript-only ingest — no hooks, proxy, or OTLP were running. Two read not_observed: a channel with a real writer that nothing in this ingest path called. Neither is a zero, and neither is left for a reader to assume from silence.

12

Integrity

What actually makes "byte-identical" a checkable claim, not a slogan.

source_db_hash: blake3:14fd056be2935fc7…
template_hash: blake3:3384a44fb8e759eb…
deterministic_render: true · llm_in_render_path: false

The report's own hash of the database it came from, plus a hash of the template that rendered it. Re-render the same database with the same renderer and these two values — and every fact above them — come out identical. That's what "same database in, byte-identical report out" cashes out to at the field level.

The second hash is worth one extra sentence, because it used to be weaker than it looked. template_hash is taken over the inlined stylesheet and page runtime themselves, not over a version label someone has to remember to bump — so changing a single CSS rule moves it. A signature that only changed when its author chose to change it would not be evidence of anything, which is exactly the failure this project spends its time avoiding elsewhere.

Why this order. Sections 11 and 12 are placed last on this page but exist first in practice — they're what tells you whether to trust sections 1 through 10 at all. bar doctor surfaces the same capture-honesty information before you even open a report.
