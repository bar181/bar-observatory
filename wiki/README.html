What it is

Think of it as the black box on an aeroplane.

The flight recorder doesn't fly the plane and it doesn't second-guess the pilot. It writes down what happened, so afterwards anyone can open it and find out.

An AI coding agent works like a very fast, very literal assistant. You ask for something; it goes away and does hundreds of small things — opening files, running commands, handing work to helper agents, fixing its own mistakes — then comes back with a summary of how it went.

That summary is written by the same agent that did the work. BAR Observatory reads the record instead, and turns it into a plain report: what was attempted, what broke, what got done twice, and what it cost.

The short version: an itemised receipt for a session of AI work — the same every time you look at it, and honest about the line items it doesn't have.

Gap 01 · Privacy

Watching costs you privacy

Most monitoring ships your code, diffs, and prompts to someone else's cloud. In a regulated shop that's not a trade-off, it's a wall.

Gap 02 · Communication

One report can't serve two readers

The person paying for the work and the person debugging it need different documents. Usually one of them gets served badly.

Gap 03 · Amnesia

Every session starts from zero

When a session ends its reasoning goes with it. The next agent re-reads the same files and repeats the same dead ends, on your budget.

One session is useful. History is better.

A single report tells you how one run went. The capture databases accumulate, and that's where the engineering signal lives: which findings keep recurring, whether your prompts and specs are actually improving, which approach converges faster, and where the same tokens get spent again and again.

Flight recorder → session observability → longitudinal evidence about how your agentic engineering is going. The MCP server's cross-run tools — compare_conditions, search_observations, list_findings, recall_context — read across every run in the index by default, so an agent starting a new session can ask "what did previous runs already try" before repeating it.

How it works

Four steps. Nothing leaves the machine.

You don't have to set anything up in advance. Claude Code already writes a transcript of every session to your own disk — BAR Observatory can read one you finished last month.

STEP 1

Point it at a session

Every Claude Code session leaves a transcript on your computer. That file is the input.

STEP 2

Read and file it

bar ingest files every event into a small local database — one per run, portable and yours.

STEP 3

Print the report

bar report calculates the report from the database. No AI is involved, which is why the output never drifts.

STEP 4

Read it, or hand it on

Open the HTML, attach the Markdown to a review, or let your next agent query the same database.

Why "deterministic" matters, without the jargon. Most tools that summarise AI work use AI to do the summarising, so the same session can produce a different write-up each time. BAR Observatory's report is calculated, not written. Run it again next year and get identical output — which is what makes it evidence rather than an impression.

Advanced — the capture and render path

Transcript ingestion is the always-on path and requires no live capture. Hooks, the proxy, and the OTLP receiver are additional channels, opt-in by design. All channels converge on one SQLite store; the deterministic render path is a pure function of that store, and the interpreted layer consumes only facts the deterministic layer has already established.

Report styles

Two audiences. Two ways of generating. Four reports.

Who a report is for and how it was generated are separate choices — and keeping them separate is what stops "AI-written summary" from quietly becoming "evidence."

Boss ModeExecutive · client
Developer GuideEngineering · debug

Evidence

A consulting-register memo of what was delivered: task completion, cost, risk flags. Every figure resolves to a row in the database. Attach it to an invoice or a pull request.

Evidence

A technical post-mortem: the chronological tool timeline, every failure with its exact sequence number, rework hotspots, and which validations actually ran.

Interpretedoptional LLM synthesis
Commentary

A narrative management summary: what the numbers mean, what needs deciding, what to keep an eye on.

Commentary

A diagnostic narrative: why the run went the way it did, and what to change in your prompts, specs, or context next time.

Each of the four renders to JSON, HTML, and Markdown from the same database in the same pass, so the three formats cannot disagree with each other.

"Boss Mode" and "Developer Guide" are this project's settled public names for the two audiences; the CLI itself still says bar interpret --audience executive|engineering — same two registers, kept identical across CLI, plugin, docs, and this page.

The line that matters

The deterministic layer is the evidence. The interpreted layer is commentary on that evidence, labelled as such, and the evidence never depends on it. Switch the LLM off, take the machine offline, or disagree with the narrative entirely — the deterministic report is unaffected.

Why an executive report isn't a gimmick

If you bill for agentic work, the artifact your client can read is the artifact that gets paid. A consulting-register memo answers "what did I get for this?" in the reader's own language, while the developer report behind it answers "what actually happened?" for whoever maintains the code. Same database, same facts, two registers.

Two readers

Made for humans. Also made for machines.

Most observability tools have one reader: a person looking at a dashboard. BAR Observatory has two, and the second one is the unusual part.

Reader 01

You

A CLI, five slash commands inside Claude Code, and an HTML report you open and read. The executive version is written for someone who has never opened a terminal.

Reader 02

Your next agent

Twelve read-only tools over the same database, served over the Model Context Protocol. The session record becomes context an agent can query instead of a picture a person squints at.

Reader 03

A swarm of agents

Agent-facing surfaces carry symbolic annotations so a coordinator and its specialists share one exact vocabulary for the artifacts they're all reading.

Closing the amnesia loop

A two-hour session ends and the next one starts blind — re-reading the same files, re-hitting the same dead ends, on your budget. Point the new session at bar-mcp and it can ask what was already tried, what failed, and why.

claude mcp add bar-observatory -- bar-mcp --db-root .bar

Twelve read-only tools. Call get_hub first — it routes an agent to everything else in the record.

Built for agentic swarms

Multi-agent systems are where ambiguity compounds fastest: a coordinator dispatching specialists needs a shared, exact description of the artifacts they're all reading, not prose each one interprets slightly differently.

Agent-facing surfaces in BAR Observatory therefore carry AISP annotations — a symbolic protocol layer that states what the record contains and how to traverse it, unambiguously.

Two rails, because they're load-bearing. AISP appears on agent-facing surfaces only — never in the human documentation path. And AISP is not a runtime dependency: every crate, command, and report works entirely without it. It's a bounded annotation layer, not a coupling. See it for real in wiki/aisp/HUB.aisp, or the protocol itself at aisp-open-core.

What the residual actually is

At the symbolic layer the remaining ambiguity isn't linguistic at all — the symbols have single definitions. What's left comes from the machine underneath: identical prompts can produce different outputs even at temperature zero, and an operating system can fail in ways no specification anticipated.

The useful part: the first of those is a known, fixable systems property rather than a law of nature. Batch-invariant inference kernels have been demonstrated to produce bit-identical outputs across a thousand repeated runs, and they now ship in the major serving engines.

What's measured, and what isn't

AISP has separately measured results for its own specification language, from the author's own research program — see aisp-open-core for that evidence. No figure from that program is reproduced on this page.

The per-layer scores above are a working estimate for this repository's documentation, not a measurement. The deep dive says so plainly, sets out the published protocol for measuring them properly, and decomposes the residual.

Get started

Your first report takes about a minute.

You don't need to clone or build anything. Install through the plugin, use Claude Code exactly as you normally would, and ask for a report when you want one. The repository holds documentation, schemas, examples, and plugin assets — the Rust source lives and publishes separately, which is why you won't find it there.

The easy way — inside Claude Code

The plugin wires everything up and adds five commands you can run without leaving your session.

/plugin marketplace add bar181/bar-observatory
/plugin install bar-observatory@bar-observatory
/bar-init

Then /bar-report for the deterministic report, /bar-interpret for the executive or engineering narrative, /bar-doctor to check the recorder, and /bar-query to ask the database a direct question.

The plugin needs the programs on your path:

cargo install bar-hook bar-mcp bar-observatory

The direct way — a terminal

cargo install bar-observatory

# set up this project (safe to re-run)
bar init --dir .

# find a session you already ran
ls ~/.claude/projects/*/*.jsonl

# read it — no API key, no network
bar ingest .bar/ambient.sqlite <session>.jsonl

# print the report
bar report .bar/ambient.sqlite --out .

Open the .html. That's your report. There's a one-script version too — see RUN.md in the repository.

The determinism contract

  • No model in the deterministic path. Report generation is a pure function of the capture database. The interpreted layer is a separate, optional command.
  • Byte-identical across formats. JSON, HTML, and Markdown render in one pass from one database, so they cannot disagree.
  • Typed contract. report.json is structured, typed output. A versioned JSON Schema for it ships in schemas/ but is currently out of sync with the live report shape — a known gap, disclosed rather than silently wrong.
  • Every claim resolves to a row. Facts carry identifiers back to the database that produced them.
  • Integrity artefacts. checksums/SHA256SUMS.txt and provenance/PROVENANCE.json ship with the repository.

Absence semantics

The schema carries an explicit absence state, and it is finer-grained than a single "missing" flag — because "we didn't look" and "we can't look yet" are different admissions:

StateWhat it meansIn the shipped report
observedthe channel had rows, and they were usedtranscripts — 9,132 turns
partialrows landed, but a measured gap was detected629 dangling parents, 136 unpaired tool_use/tool_result
not_recordedthis channel had no rows in this storehooks, events, spans, requests on a transcript-only ingest
not_observeda writer or detector exists, but nothing invoked it hereplan_docs, raw_logs, and the two unbuilt detectors

None of the four is ever coerced to zero, empty, or unchanged. This is a design rule with teeth: a cost figure of $0.00 and a cost figure of not_recorded mean entirely different things, and conflating them is how observability tools quietly lie. bar doctor makes the distinction visible before you read a report, and the report's own capture-quality table repeats it channel by channel with the reason attached.

Capture channels

  • Transcript ingest — always on, zero network calls, retroactive. The primary path.
  • Lifecycle hooks — 21 events, wired by the plugin. Unresolvable hook commands fail harmlessly and never block a session.
  • Proxy — opt-in ANTHROPIC_BASE_URL interception for request-level detail.
  • OTLP receiver — opt-in, native, for OpenTelemetry-emitting sources.

Known limits, on the record

  • Model-side delivery failures are invisible. Results that failed to reach the model's context but were recorded correctly server-side don't appear. Disclosed as a candidate detector.
  • Plugin binaries resolve via PATH. No release pipeline assembles per-platform binaries into the plugin zip yet.
  • Optional modules are off by default. The always-on path is transcript parsing only.
  • The interpreted layer is commentary, not evidence, and is labelled as such wherever it appears.

Questions

Frequently asked.

Do I have to change my code to use this?

No. There's no SDK, no import, no decorator, and no trace context to thread through your application. BAR Observatory watches the Claude Code runtime through its plugin and hooks, so your project is untouched — and stays untouched if you uninstall.

Does BAR Observatory send my code anywhere?

No. The main path reads a file that's already on your disk and makes zero network calls. No account, no API key, no usage telemetry. MIT-licensed, so you can check that rather than trust it.

Can it run fully offline or air-gapped?

Yes. Capture, storage, and the deterministic report all work offline. The only network-dependent piece is the optional interpreted layer, which you can leave switched off entirely.

Do I need Docker, Postgres, or a background server?

No. A compiled binary and an embedded SQLite file. Nothing to keep alive.

Can I get a report for a session I already ran?

Yes — the quickest way to try it. Point it at any Claude Code transcript on your disk and you'll get a report straight away, even though nothing was recording at the time.

Where does Claude Code keep session transcripts?

In your ~/.claude/ folder, one .jsonl per session, organised by project. ls ~/.claude/projects/*/*.jsonl lists them.

What's the difference between the deterministic and interpreted reports?

The deterministic report is calculated: no AI, costs nothing, identical every time, safe to treat as evidence. The interpreted report is optional AI synthesis that turns those same facts into a narrative for an executive or an engineer. The evidence never depends on the commentary.

What do not_recorded and not_observed mean?

Two different things, kept apart on purpose. not_recorded means the channel had no rows in this store — you weren't running the proxy, so there are no token counts. not_observed means the machinery exists but nothing invoked it here. Neither is ever printed as a zero you might mistake for a real measurement. Absence is reported as absence, and the report says which kind.

Is this a replacement for Langfuse, AgentOps, or a hosted tracer?

No — different job and a different integration model. Those instrument applications you build. BAR Observatory watches the agent you use. Plenty of teams run both.

How does an AI agent use this?

Through bar-mcp: twelve read-only tools over the capture databases, with get_hub as the entry point. Agent-facing surfaces additionally carry AISP annotations for swarm coordination — never as a runtime dependency.

Is BAR Observatory made by Anthropic?

No. An independent open-source project by Bradley Ross, built for Claude Code but not endorsed by or affiliated with Anthropic.

How do I get help?

Open an issue on the repository. Security reports have their own process in SECURITY.md, and contribution guidance is in CONTRIBUTING.md.

AISP is a surface, never a dependency

aisp∈surface(agent)∧aisp∉surface(human) and aisp∉runtime(bar-*). Every crate, command, and report works with AISP absent. The notation binds what agents read, not what the software needs.
