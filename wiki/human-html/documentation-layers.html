Wiki · documentation architecture · AISP

Written three times, on purpose.

The words that make a sentence clear to a person are the same words that make it ambiguous to a model. BAR Observatory's documentation therefore exists in three registers — human prose, structured agent-facing docs, and AISP symbolic specifications — describing one set of facts so they don't drift apart in meaning, even though today they're written by hand rather than generated from a single source.

This page explains why, what each layer costs and buys, what the residual ambiguity in a symbolic specification actually consists of, and — the part usually skipped — how you would measure any of it rather than assert it.

Modelled

The per-layer scores on this page (58 / 20 / 1.8) are a working estimate for this repository's documentation. They are an analytical model, not a measurement, and are labelled as such throughout.

External

The residual decomposition draws on published work on inference determinism, cited by name and linked in the References section below.

AISP has separately measured results for its own specification language, from the author's own AISP research program — see aisp-open-core for that evidence; no figure from that program is reproduced on this page. Distinguishing a modelled estimate from an externally-sourced claim is the same discipline the product applies to its own reports: a number you measured and a number you modelled are different objects, and collapsing them is how a claim quietly becomes a lie.

Why three

"Initialise the database cleanly."

That sentence is good human writing. It is also close to useless as an instruction to a machine, and the reason is worth being precise about.

A person resolves "cleanly" from context in about a tenth of a second. A model has to choose between at least three functionally different behaviours: delete the existing file and start fresh, apply pending migrations to what's there, or leave the data alone and set the journal mode. Each is a defensible reading. Each produces a different program. And crucially, the same model asked twice may choose differently — so the failure isn't a misunderstanding you can correct once, it's a variance you inherit forever.

This is a well-studied phenomenon in requirements engineering, not a novel claim. The field's formal definition is exactly the one that matters here: a requirement R is ambiguous for code generation when two valid interpretations of it produce functionally different programs.

R is ambiguous  ⟺  ∃ I, I′ ∈ 𝕀(R)  such that  FI ≠ FI′

Recent benchmark work confirms the practical cost: ambiguity degrades code generation across every model tested, with the most pronounced effects on the most capable models, and models largely fail to notice or resolve the ambiguity on their own. Capability does not rescue you from an under-specified instruction — if anything, a stronger model fills the gap more confidently.

The design consequence. You cannot fix this by writing better prose, because the properties that make prose good for humans — economy, implication, adjectives that compress context — are the properties that create interpretive fan-out. The fix is to write a different artefact for the machine, describing the same facts. Not a translation. Not a summary. A different register of the same truth.

The layers

Three registers, one set of facts.

The same instruction, expressed for each reader. Note that the layers get longer and less pleasant to read as they get less ambiguous. That trade is the whole point, and it's why you keep all three rather than picking one.

Hand-maintained today, not generated. Unlike this project's reports — which are a pure function of a capture database and cannot drift by construction — these three documentation layers are currently written and kept in sync by hand. That's a real difference worth stating plainly rather than implying otherwise: hand-maintained parallel documentation can drift, and a drifted machine-facing layer is worse than no machine-facing layer, because an agent will follow it confidently. There is no generation pipeline or drift gate wired up for these three layers today. If one gets added, this note is exactly where that would be disclosed.

The residual

What the last two points actually are.

At the symbolic layer the semantic ambiguity approaches zero — ∃, ⊢, and a state mapping have single non-subjective definitions, and there is no adjective left to interpret. So what's left?

Not language. The residual comes from the machine the language runs on, and it splits into two unrelated causes with very different outlooks.

Residual 01

Inference non-determinism

~1.0OF 100 · ESTIMATED SHARE

Identical inputs to an identical model can produce different outputs, even at temperature zero. Where the specification's meaning is fixed, the generation of a response to it still varies at the systems level — token ordering around operators, whitespace, incidental syntax.

Residual 02

Environment boundary faults

~0.8OF 100 · ESTIMATED SHARE

A specification bounds a state transition, S₀ → S₁ | S₁ ⊢ P. It cannot bound what happens outside its predicate space. An out-of-memory kill, a disk write timeout, a kernel permission error — the agent meets a condition the spec never described, and must improvise a fallback.

The 1.0 / 0.8 split is a modelled attribution, not a measured decomposition. It apportions an observed total; it does not derive from separate experiments on each cause. Treat the ratio as an argument about which cause dominates, not as a result.

Residual 01, corrected: it isn't what most people think

The standard explanation for temperature-zero non-determinism is "floating-point addition isn't associative, and GPU threads finish in non-deterministic order." That explanation is intuitive, widely repeated — and, as of the current literature, largely wrong. It's worth stating correctly here, because getting it right makes the AISP position stronger, not weaker.

The forward-pass kernels are in fact reproducible run to run. You can check this yourself: multiply the same two matrices a thousand times on a GPU and the results are bit-identical every time.

# the "GPU concurrency causes chaos" hypothesis, tested directly
A = torch.randn(2048, 2048, device='cuda', dtype=torch.bfloat16)
B = torch.randn(2048, 2048, device='cuda', dtype=torch.bfloat16)
ref = torch.mm(A, B)
for _ in range(1000):
    assert (torch.mm(A, B) - ref).abs().max().item() == 0   # passes, 1000/1000

The actual cause is batch invariance failure. A serving engine continuously rebatches incoming requests: your prompt might run alone in one step and alongside two others in the next. Reduction kernels tile their work according to the current batch size, so a different batch means a different reduction tree, which means the same floating-point values get summed in a different order. Your output depends on who else was querying the server at that moment — which is why it looks random and isn't.

The measured effects are not marginal. A thousand identical temperature-zero requests to a large open-weights model produced 80 distinct completions, diverging at around the hundredth token. Related work has documented accuracy swings of several percent and large output-length gaps purely from changing GPU count or batch size.

Why this correction strengthens the argument. If the residual were floating-point physics, it would be a floor — irreducible, and a permanent ceiling on any claim of specification determinism. It isn't. Batch invariance is a missing property of kernels, and it has been fixed: batch-invariant implementations of matmul, RMSNorm, and attention produce bit-identical outputs across a thousand repeated runs, and now ship as an open-source reference implementation (linked below). The reported cost is throughput — roughly 61% overhead in the original implementation, cut to about 34% once integrated with CUDA graphs.

So Residual 01 is not a law of nature. It is a purchasable property. On a deterministic serving stack it approaches zero, and the honest form of the AISP claim becomes: semantic ambiguity is eliminated by the specification; generation variance is eliminated by the serving configuration; what remains is Residual 02 alone.

Residual 02: the part that stays

Environment faults are a genuine boundary, and no specification language closes them, because the fault occurs in a space the specification does not describe. A predicate over database state says nothing about what to do when the kernel kills the process mid-write.

What a good specification can do is make the boundary explicit rather than implicit — declare the fault classes it does not cover, so that an agent meeting one knows it has left the specified region instead of improvising inside it and believing it complied. That converts an unbounded failure into a detected one.

This is precisely the same discipline as not_observed in BAR Observatory's reporting layer. In both cases the design rule is: an unrepresented condition must be visibly unrepresented, never silently filled in. A spec that quietly covers a fault it cannot really handle is the documentation equivalent of reporting $0.00 for a channel you never captured.

How to measure it

Turning the estimate into a result.

The 58 / 20 / 1.8 figures above are an analytical model. They're defensible as a model — the ordering is certainly right and the magnitudes are plausible — but they are not a measurement, and this section exists so that nobody has to take them as one.

The good news is that the measurement is well-defined and the literature has already settled the metric. It is a run, not a research programme.

The metric: semantic entropy over functional clusters

Do not try to score ambiguity by inspecting the text. Score it by what the text causes. Generate many implementations from the same instruction, cluster them by functional equivalence rather than surface form, and take the entropy of the cluster distribution. A single cluster means one interpretation: zero ambiguity. Many clusters of similar mass means the instruction genuinely fans out.

SE(R) = − Σy m≡(y | R) · log m≡(y | R)   ;   ambiguous(R) ⟺ SE(R) > 0

This follows the semantic-entropy family of uncertainty metrics — scoring a generator by the entropy of meaning clusters in its outputs rather than surface text — adapted here to code: an instruction counts as ambiguous when it yields more than one functional-equivalence cluster of programs. It has the property you want: it is behavioural, so it cannot be gamed by writing text that merely looks precise, and it produces a continuous score rather than a verdict.

The protocol

  1. Fix a task set. Draw N real instructions from this repository's own documentation — ones that already exist in all three layers. Twenty is enough to be indicative; a hundred is enough to publish.
  2. Hold everything constant but the layer. Same task, same model, same serving configuration, same generation settings. The layer is the only independent variable. This is the step most comparisons get wrong.
  3. Generate k implementations per instruction per layer. k = 20 is the common choice; more is better and the cost is linear.
  4. Cluster by functional equivalence, not text. Run the generated programs against a differential test suite; two outputs are the same cluster when no input distinguishes them. Never cluster on string similarity — that measures phrasing, not meaning.
  5. Compute semantic entropy per instruction, then aggregate per layer. The result is three distributions, which is a far stronger claim than three point scores.
  6. Report the residual separately. Run the same protocol on a batch-invariant serving stack. The difference between the two runs is Residual 01, measured rather than apportioned — which also settles the 1.0 / 0.8 split honestly.
  7. Cross-vendor replication. Repeat on three model families — see aisp-open-core for the author's separate AISP research program, which follows the same cross-vendor discipline.
Off-the-shelf control. A published benchmark of function-level tasks paired with deliberately ambiguous requirement variants — covering lexical, syntactic, semantic, and vagueness ambiguity — already exists, at roughly 1,300 tasks and 5,200 variants (linked below). Running AISP-specified versions of those same tasks against the natural-language originals would produce a comparison against an independent, externally constructed baseline rather than one of your own design. That is the single highest-credibility experiment available here, and it is a weekend of compute.

What a fair result would look like

Stated in advance, because pre-registering the expectation is what separates a measurement from a demonstration:

  • Expected: semantic entropy strictly ordered Human > AI > AISP across the task set, on every model family tested.
  • Expected: AISP entropy at or near zero on a batch-invariant serving stack, and non-zero but small on a standard one.
  • Would falsify the strong claim: AISP entropy indistinguishable from the AI layer — which would mean the structure, not the symbols, is doing the work.
  • Would falsify the residual model: AISP entropy unchanged between standard and batch-invariant stacks — which would mean Residual 01 is misattributed.
  • Known confound: models may have seen more prose than symbolic specs in training. Report per-family results; do not average the confound away.
Say the grade out loud. Until that run exists, every per-layer number on this page should carry the word estimated. Publishing a modelled figure as a measured one is the fastest way to lose the argument to the first reader who asks how it was obtained — and the AISP result is strong enough on its measured evidence that it does not need the borrowed authority.

References and provenance

Where these claims come from.

  • Inference non-determinism and batch invariance — Thinking Machines Lab, "Defeating Nondeterminism in LLM Inference" (2025), and the accompanying batch_invariant_ops reference implementation. Source of the 80-distinct-completions result, the bit-identical-across-1,000-runs result, and the ~61% / ~34% overhead figures.
  • Ambiguity in requirements and its effect on code generation — the four-type ambiguity taxonomy (lexical, syntactic, semantic, vagueness) and the ~1,300-task / ~5,200-variant benchmark: "Assessing the Impact of Requirement Ambiguity on LLM-based Function-Level Code Generation". The formal definition of ambiguity via functionally divergent interpretations, and the finding that ambiguity degrades performance most on the most capable models, follow the same line of work.
  • Semantic entropy as an uncertainty metric — the general semantic-entropy family of metrics that score a generator by the entropy of meaning-equivalence clusters rather than surface text, adapted here from natural-language uncertainty estimation to functional-cluster entropy over generated code. Cited by concept rather than a single paper; the protocol above is this repository's own adaptation, not a reproduction of a specific published pipeline.
  • AISP's own measured results — a separate, author-run research program has its own measured evidence for its symbolic specification language. Not reproduced here, and no figure from that program appears on this page — see aisp-open-core for the evidence itself.
  • Modelled, not measured — the 58 / 20 / 1.8 per-layer scores and the 1.0 / 0.8 residual split. Analytical estimates for this repository's documentation, pending the protocol in the previous section.
